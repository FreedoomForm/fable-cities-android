# Native Android Port

## Current milestone

The repository ships a **dual-track APK**:

- **Track A — web-parity launcher (`ParityActivity`, the launcher icon).** The user's acceptance criterion is a 1:1 visual match with the browser game ("сохранив визуал один в один"). The browser game's look is produced by a three.js PBR + CSM + bloom + SMAA stack that a hand-written GLES renderer can not reproduce quickly, so the full production web build (`vite build` output, ~208 MB incl. CC0 texture sets and models) is bundled into the APK at CI build time (`android/app/src/main/assets/web/`, generated — never committed) and served offline through `WebViewAssetLoader` (`https://appassets.androidplatform.net/assets/web/`). ES modules, fetch and localStorage need a real http(s) origin, which `file://` cannot provide. Touch mapping: one finger = the page's native pointer behaviour (tools, UI); an injected shim maps pinch → wheel (zoom) and two-finger drag → middle-button drag (pan, the desktop camera binding); the Android Back button dispatches Escape (menus). This track is not a substitute for the native renderer — it is the user-facing visual-parity deliverable and is explicitly allowed by the user's clarified priority, superseding the original "no WebView at all" reading for this track only.
- **Track B — native GLES renderer (`MainActivity`, adb-launchable, CI-gated).** A real Android `Activity`, an OpenGL ES 3.0 renderer, and a Canvas HUD overlay. `GlCityRenderer` renders through a GLES 3.0 pipeline on a `GLSurfaceView`: a deterministic seeded 96×96 terrain heightfield, a coastal water plane with animated Fresnel shading, a ray-marched sky gradient, distance fog, ~a hundred seeded buildings whose windows glow warm at night, and 26 deterministic vehicles. It computes a bounded 16:9 viewport at runtime and letterboxes rather than stretching. A Canvas-drawn HUD overlay provides large labelled touch controls above the GL surface. Porting the full three.js visual stack natively (PBR, cascaded shadow maps, GTAO, bloom, SMAA) remains the long-term goal of this track and is worked in parity slices.

## UI conversion decisions

The native HUD uses large labelled controls instead of the browser game's dense desktop toolbar. The essential tools are Select, Road, Zone, Service, and Bulldoze. Each tool is reachable from the bottom dock, reports its active state, provides a short action hint, and can be operated without a mouse, keyboard, hover state, or right-click. One-finger drag pans, pinch zooms, two-finger twist rotates, two-finger vertical drag pitches, and single taps apply the active tool through ray picking. Tool actions give immediate visible feedback through the message panel and city counters.

This is intentionally a redesign rather than a pixel-for-pixel port. A desktop layout can render on a phone while still requiring cursor precision, hover discovery, or keyboard shortcuts. Those interactions are not reliable on a touch screen, especially when the player is holding the device in landscape. The native layout therefore reserves a large bottom interaction band, keeps the city visible above it, uses explicit labels, and gives each action a pressed/selected visual state.

## Next port slices

1. Exercise both tracks on an emulator/device: CI runs an `emulator-smoke` job on every push (API 34 x86_64, KVM, swiftshader GPU): it installs the APK, boots the web-parity launcher first (90 s soak — three.js first boot is slow on swiftshader; gates: process alive, zero page console errors, screenshot), then force-stops and boots the native activity (20 s soak; gates: process alive, zero fatal/native-signal lines, zero `GlCityRenderer` shader/link/GL-error lines, screenshot). An APK that fails either gate is never published. Still open: rotation policy, background/resume stress, real-device frame pacing. DONE: parity-track twist→rotate (two-finger twist maps onto the web right-drag yaw binding once ~12 deg of twist accumulates).
2. **Native world parity — DONE (round 2).** `worldgen/` is a bit-exact Kotlin port of the browser game's world core: `shared/random.js` (mulberry32 + hash2), `shared/noise.js` (simplex 2D/3D, fbm, ridged), and `terrain/Heightmap.js` (the full analytic generator, grid generation, `getHeight`/`getSlope`, `flattenRect`/`conformPath`/`conformDisc`, `averageHeight`). Golden JVM tests (`WorldGenParityTest`) pin RNG/hash2/simplex/sampleGen/grid/conformPath to values produced by the actual web code in Node (seed 1337) and run on every CI push. The native scene renders the site's real world: coastal plain, meandering river, sea to the south, terraced mountains north; the prebuilt avenue/streets conform the terrain through the site's own `conformPath`; buildings, vehicles and the tool grid sit on real heights. Not yet ported from Heightmap.js: `raycast` (the renderer uses its own ray-march), `computeShoreDistance`, and the outer horizon-ring coarse grids.
3. **Native demo city + simulation — DONE.** `DemoCity.kt` ports the web `DemoCity.js` (u,v) road layout, trumpet interchange, block plan and routes bit-exactly (site picker pinned by `SitePickerParityTest` goldens). `Simulation.kt` ports the web simulation core: `services.js` (16 m coverage grids, capacity strain, upkeep), `economy.js` (household occupancy model, jobs, RCI demand, happiness, weekly budget) and `milestones.js` (population thresholds with rewards, alerts). `SimulationParityTest` runs the REAL web modules headless in Node (probe_sim.mjs) with the site's own sim RNG chain (`world.rng.fork(hashString('simulation'))`) and pins checkpoints at 24/72/168/336 game hours. In-game: 3 game minutes per real second (the site's secondsPerHour=20), demo blocks + painted zones feed the economy, the SERVICE tool places the site's 8 real service types at their real costs, road upkeep uses the web ROAD_COST table, the HUD shows live money/population/milestone from the model, and milestones pay real cash rewards.
4. **Native environment — DONE (clear weather).** `Environment.kt` ports `environment/atmosphere.js` bit-exactly (single-scattering sky, transmittances, sun+moon ephemeris, exposure curve, nightFactor) plus the clear-weather branch of `environment/index.js` computeFrame/sampleSkyAverages (sun/moon intensity + colour keys, hemisphere sky/ground, twilight floor, golden-hour tints, aerial-perspective fog). `EnvironmentParityTest` pins 9 probed hours + direct sky-radiance probes against Node goldens at the site's defaults (hour 14, doy 121, lat 47.3, clear preset). The renderer's invented sun state is gone; sky dome, fog, water and window lights are driven by the real model. Open: weather transitions (cloudy/rain/fog/snow), volumetric clouds, star field.
5. **Terrain ground palette — ported (approximation).** The native terrain vertex colors now follow the site's TerrainMaterial.js splat tints (olive meadow ↔ straw grass, ragged waterline sand, silt bed, wet band, ochre→granite rock strata, snow line wandering ±100 m around 172 m, regional colour drift) driven by the real heightfield. Open: the full splat GLSL with the 8 CC0 texture layers, normal maps and canopy weights.
6. **Parity APK size — DONE.** CI downscales every bundled texture to 1024 px after `vite build` (measured 187 → 42.7 MB on the real asset set; formats and filenames untouched so GLTF references keep resolving). The web-parity APK drops from ~200 MB to well under 100 MB.
7. **Native water — DONE (clear weather).** `worldgen/Water.kt` ports the web water stack bit-exactly (pinned by `WaterParityTest` against `tools/probe_water.mjs` goldens): `Heightmap.computeShoreDistance` (exact Felzenszwalb EDT shoreline SDF, Uint8 payload 128 + 4·sd), `textures.js makeNoiseTexture` (tileable RGBA fBm) and `makeWaterNormalTexture` (18 deterministic directional waves), the `Water.js _buildGeometry` quad scan (128 m chunks dipping below waterLevel + 0.8 plus the 4 horizon-ring quads) and `THREE.DataUtils.toHalfFloat`. `GlCityRenderer` renders the site's water through the same physical structure: per-pixel depth from an R16F height texture (dark teal → navy absorption ramp on 0x13282f, river bed in the first metre, 0.30 desaturation), five ripple octaves from the site's own 18-wave normal map (150 m swell → 2.4 m chop, the 23/61 m layers never fade), fresnel-weighted analytic sky probe desaturated to the site's slate chroma, a tight GGX glitter lobe for the sun AND the real moon, the noise-broken ≤ 1.6 m foam lace + rare whitecaps driven by the shore SDF, the absolute sky-bounce floor and luminance-normalised night sheen, and the dithered waterline dissolve. Remaining: planar reflection RT, weather terms (rain dimples/roughness), waterline SDF recompute after terrain edits.
8. **Native night sky — DONE.** `worldgen/Stars.kt` ports `environment/StarField.js` bit-exactly (pinned by `StarParityTest` against `tools/probe_star.mjs` goldens): the Milky Way cube map (galactic frame tilted 62.9°, seeded roll, dust lanes via the site's own simplex fBm, warm bulge, chroma+alpha encode at STAR_ALPHA_SCALE 0.7) and the 512×256 moon albedo map (highlands, maria, 180 craters with floors/rim/ejecta, pole longitude-stretch). `GlCityRenderer`'s sky now draws the site's full night: the procedural star field (pixel-exact cube-face grid with spectral colours, magnitude distribution and twinkle) plus the baked Milky Way rotating with the REAL sidereal angle (`Environment.EnvState.siderealAngle`), washed out by sky luminance exactly like the web; the phase-correct moon disc (limb darkening, earthshine, uMoonBright) with its triple-exponential halo; and the sun disc with limb darkening and the 2200 K golden-hour tint. Remaining: cloud shadowing of stars, star wash under future cloud decks.
9. Next slices: buildings/traffic module ports (replacing the placeholder vehicles), weather transitions, planar reflection RT, frame-time instrumentation to `docs/STATUS.json`.

## Verification status

This environment has no Android SDK, Gradle executable, or ADB/emulator. The GLES 3.0 renderer, GLSurfaceView conversion, HUD overlay, gesture handling, and persistence were reviewed line-by-line for API and Kotlin consistency, and the browser modules continue to pass `npx vite build`. Android compilation is verified by the GitHub Actions workflow on every push, which also publishes the APK as a commit-linked prerelease. Installation, on-device screenshots, frame-count verification, and crash monitoring now run in CI on every push via the emulator gate; rotation/background-resume stress and real-device frame pacing remain explicit follow-up gates and must not be reported as passed until exercised.
